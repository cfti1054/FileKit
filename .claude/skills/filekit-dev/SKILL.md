# 변환툴 개발 오케스트레이터

**실행 모드: 서브에이전트 위임 (전문가 풀 + 분산·통합).** 단계마다 `Agent` 도구로 `.claude/agents/`의 전문 에이전트를 부른다. 에이전트끼리 대화할 필요가 없고, 경계 인터페이스를 설계 단계에서 먼저 확정하므로 구현 단계는 소유 영역별로 병렬 실행한다. 단계 사이 데이터는 `_workspace/` 파일로 넘긴다.

## 에이전트 구성

| 에이전트 | 모델 | 맡는 일 | 수정 권한 |
| --- | --- | --- | --- |
| `architect` | opus | 요구사항 연결, 경계 인터페이스, 작업 배정, 병렬·순서 판단 | 없음 |
| `core-dev` | opus | `Cargo.toml`, `core/`, `cli/`, 엔진 어댑터 | 자기 영역 |
| `win-dev` | opus | `app/src-tauri/`, `installer/` | 자기 영역 |
| `ui-dev` | sonnet | `app/ui/` | 자기 영역 |
| `qa-reviewer` | opus | 자동 검사, 경계 대조, spec 제약 검사 | 없음 |

모델은 업무 성격으로 골랐다. 인터페이스 설계, 동시성·프로세스 코드, Win32·COM, 교차 검증은 opus, 수치가 정해진 화면 구현은 sonnet이다.

공통 규칙은 `filekit-conventions`, 영역별 방법은 `engine-adapter`, `win32-integration`, `radial-menu-ui` 스킬에 있다. 각 에이전트 정의가 어떤 스킬을 읽을지 정해 두었으므로, 오케스트레이터는 스킬 내용을 프롬프트에 복사하지 않는다. 그래야 메인 컨텍스트가 가볍게 유지된다.

## 0단계: 현재 상태 확인

1. `_workspace/`를 확인한다.
   - 없으면 처음부터 실행한다.
   - 있고 일부만 고쳐 달라는 요청이면 해당 단계나 에이전트만 다시 실행한다.
   - 있고 새 요청이면 `_workspace/`를 `_workspace_{YYYYMMDD_HHMMSS}/`로 옮긴 뒤 새로 실행한다.
2. `git status`로 사용자의 진행 중 변경을 확인한다. 덮어쓸 위험이 있으면 먼저 알린다.
3. 요청이 한 영역의 작은 수정(파일 1~2개, 인터페이스 변화 없음)이면 1단계를 생략하고 해당 개발 에이전트 하나와 QA만 부른다. 에이전트 호출 비용을 작업 크기에 맞춘다.

## 1단계: 설계

`architect`를 부른다. 사용자 요청 원문, 관련 spec 장, 기존 `_workspace/` 결과 경로를 넘긴다.

- 반환된 계획을 `_workspace/01_architect_plan.md`에 그대로 저장한다.
- "확인 필요"가 작업 전체를 막으면 사용자에게 묻고 멈춘다. 일부만 막으면 나머지를 진행하고 보고에 남긴다. "가정"은 그대로 진행한다.

## 2단계: 구현

계획의 「작업 배정」과 「실행 순서」를 따른다.

- 순서 의존이 없는 에이전트는 **한 메시지에서 병렬로** 부른다(예: `core-dev`, `win-dev`, `ui-dev` 동시).
- 같은 영역 안에서도 서로 독립인 파일 묶음(예: 엔진 어댑터 4개)은 같은 에이전트를 파일 범위를 나눠 병렬로 부를 수 있다. 공용 파일(`mod.rs`, `Cargo.toml`)은 한 인스턴스만 맡게 정한다.
- 순서 의존이 있으면 앞 작업이 끝난 뒤 부른다. 예: 코어 API를 새로 만들면 `core-dev` → `win-dev`.

각 에이전트 프롬프트에 넣을 것:
- `_workspace/01_architect_plan.md` 경로와 자기 담당 절 이름
- 맡은 파일 범위(병렬 분할 시)
- 결과 보고는 에이전트 정의의 출력 형식으로

같은 Cargo 워크스페이스를 병렬로 빌드하는 에이전트에게는 인스턴스마다 다른 `CARGO_TARGET_DIR`(`target/b1`, `target/win`, `target/qa` 등)을 지정한다. 하나의 target 폴더를 같이 쓰면 빌드 잠금 때문에 서로 기다린다. 또 프롬프트에 `cargo update` 금지를 넣는다. `Cargo.lock`의 버전 고정이 GNU 툴체인 빌드를 지탱한다(`filekit-conventions` 「검사 명령」).

결과를 `_workspace/02_{agent}_impl.md`에 저장한다(같은 에이전트를 나눠 불렀으면 `02_{agent}-{범위}_impl.md`). 어느 에이전트가 "인터페이스 변경 필요"를 보고하면 `architect`에게 그 항목만 다시 판단받고 영향받는 에이전트에 전달한다.

## 3단계: 검증

`qa-reviewer`를 부른다. 변경 파일 목록, 각 `02_*` 결과 경로, 계획의 「검증 포인트」를 넘긴다.

- 결과를 `_workspace/03_qa_report.md`에 저장한다.
- **통과**면 4단계.
- **수정 필요**면 발견 사항을 `[담당]`별로 묶어 해당 에이전트들에 (독립이면 병렬로) 돌려보낸 뒤 QA를 다시 부른다. 재검토 결과는 `03_qa_report_r2.md`.
- 같은 항목이 두 번 연속 실패하면 자동 수정을 멈추고 사용자에게 보고한다.

## 4단계: 보고

최종 응답에 담는다.
- 요청을 어떻게 이해했는지, 고른 가정
- 변경 파일 목록 (영역별)
- QA 자동 검사 각각의 실제 결과 (실패·실행 불가 포함)
- 확인하지 못한 부분과 수동 확인 목록 (실제 탐색기, 100ms 측정, 실제 엔진 변환 등)
- 커밋이 필요하면 `filekit-conventions` 형식의 메시지를 제안한다. 커밋과 푸시는 요청받을 때만 한다.

## 오류 처리

- 에이전트가 실패하거나 응답이 없으면 한 번 다시 부른다. 또 실패하면 `_workspace/`에 실패 기록을 남기고 그 결과 없이 진행한 뒤 보고에 누락을 적는다.
- 사용량 한도, 인증 만료, 권한 거부는 다시 시도하지 않는다. 부분 산출물을 직접 열어 어디까지 됐는지 확인하고 보고한다.
- 에이전트가 확인하지 못한 사실을 오케스트레이터가 추측으로 채우지 않는다. "확인 안 됨"으로 둔다.
- 빌드 환경 문제(MSVC, WebView2 없음 등)로 앱을 빌드할 수 없으면 코어·CLI·UI 검증만으로 진행하고, 막힌 검사와 해결 방법을 보고한다.

## 테스트 시나리오

**정상 흐름:** "WEBP 출력에 품질 프리셋을 추가해줘"
1. `architect`가 F-08과 연결하고, `presets.rs`·`engines/vips.rs`만 바뀌며 인터페이스 변화가 없다고 계획한다.
2. 0단계 3번 기준에 따라 작은 수정이면 `core-dev` 하나만 부른다.
3. `qa-reviewer`가 fmt·clippy·test와 명령 생성 테스트를 확인한다.
4. 변경 파일과 검사 결과를 보고한다.

**오류 흐름:** "여러 파일 선택 시 공통 형식만 메뉴에 보여줘"
1. `architect`가 코어(공통 형식 계산 API), 앱(선택 항목 전달), UI(허브 개수 표시) 세 영역에 걸친다고 계획하고, 코어 API 시그니처를 먼저 확정한다.
2. 인터페이스가 확정됐으므로 세 에이전트를 병렬로 부른다.
3. QA가 Tauri 이벤트 페이로드와 `ipc.ts` 타입 불일치를 찾는다 → `ui-dev`에게만 돌려보낸다.
4. 두 번째 QA에서도 같은 항목이 실패하면 자동 수정을 멈추고 사용자에게 보고한다.

## 후속 요청 처리

"다시 실행", "재검증", "보완", "UI만 다시", "이전 결과 기반으로 수정" 같은 요청은 0단계로 돌아가 `_workspace/`를 확인하고 필요한 단계·에이전트만 다시 부른다.
